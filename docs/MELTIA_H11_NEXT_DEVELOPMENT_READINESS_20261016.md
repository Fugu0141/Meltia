## 1. 目的、スコープ、保留する判断

- **目的**：H11の観測された境界精度を失わず、保守性・可観測性・実行速度・テストの信頼性を段階的に改善する。H12の追加機能やスコア改善は**次期バージョンの要件定義で**選択し、独断で本体へ搭載しない。
- **対象**：`src/Meltia.Core/Boundary/`の研究エンジン、検証ランナー、実験・設計文書。既存`MeltiaBoundaryEngine`とWindows Previewの安定した入力経路は、明示的な別計画までは保持する。
- **非対象**：製品名・UI変更、ネイティブMeltypeの大規模移植、本番IME/TSFへのH11接続、辞書の個別単語追加で診断集合を暗記する改修、既存GitHub Releaseの変更。
- **採用判定**：mainにH11のコードが存在することと、Preview/IMEがH11を採用したことは**別**。H11は現在`AutoCommitAllowed == false`の独立試作で、IME実キー・Windows E2E・独立自然文評価は未完了。
- **研究記録**：重要な根拠・選択したトレードオフ・不採用案・回帰テスト・測定条件をすべてMarkdownに残す。外部AIの意見は検証済みの事実として扱わない。

## 4. 次期開発の作業順序（小PR・依存関係・完了条件）

原則、各PRを独立してレビューできる規模に限定する。**異なるPRで同じソースファイルを並列編集しない。** コード変更時は最新mainから専用ブランチを作り、実装前に要件・基本設計をMarkdownへ追記してから着手する。

### Phase 0 / P0 — 基準固定・測定器具の用意

**PR-A：ベースラインの契約テストとメタデータ**

1. PR #34のH11出力を再実行し、103ケースについて`Top1`/`Top-K`/`候補スパン`/`needs_confirmation`と未解決リストを、順序・同点処理も含めて機械比較できる形式で保存する。テストハーネスの検証にgold以外のヒントを入力しない。
2. 旧v1.0・H10・H11の入力・証拠を同一にし、辞書ファイルとモデル/データセットをハッシュで固定する。**出力差分ゼロのリファクタリング**と**精度改善を意図する変更**を別々のPRで扱う。
3. ベンチマークにはraw長 **32/128/256/512/1024 UTF-16単位**、英語・日本語・日英混在・URL・記号・絵文字、カーソル移動・貼付け・削除を含める。プロセスのウォームアップ、反復数、GC/割り当て量、p50/p95/p99、CPU、SDK、Releaseビルド、コミットSHAを記録。測定時の入力長上限は実装どおり守る。
4. **非公開の自然文holdoutの収集仕様をここで先に固定**：出典・許諾、文字種・分割単位・意図ラベル・複数意図、重複排除、辞書命中のタグ、収集日時、dev/test分離、評価時までtestを見ない手順を定義。ユーザーの私的な打鍵ログは含めない。

**合格**：診断103件で旧コミットと結果・例外・ロック・Unicodeの差分ゼロ。ベンチ結果は測定条件付きで記録され、精度指標にラベルなし検査を混入させない。

### Phase 1 / P0 — スコア差分・探索理由を説明できるようにする

**PR-B：DiagnosticTrace（推論結果を変えないオフライン機能）**

- H11候補の`raw_utf16_span`、`language`、`origin`、辞書/文字尤度/長さ/音韻適合/継ぎ目/大文字/構造/ロック別の**名前付き寄与値**をJSONへ出す。加法スコアの**合計が旧計算値と一致**する不変条件を設ける。
- 言語遷移コスト、遷移前状態、累積スコア、候補除外理由、ビーム脱落の位置と理由、同点ルール、Top1/Top2差分を記録。ルート全体の差は単一候補の差と混同しない。
- Goldは推論には供給せず、**解析後だけ**Top1との差分を出す。Goldに整合する経路が元の候補グラフで存在するかを判定し、存在する場合に最良のGold制約付きスコアとTop1との差を出す。存在しなければ`missing_candidate`と`path_pruned`を区別する。**不足するGold候補を仮生成してスコア比較しない**。
- 通常実行ではトレース無効。**パスワード・私的入力をログに保存しない**。CI専用の公知/合成ケースだけ保存。重い解析をホットパスに入れない。
- `yaml`/`new`/`hotelltu`/`Are you sushi?`／`handanwodelegatesuru`などの説明レポートを生成する。

**合格**：トレースON/OFFで全103件のルート（スパン/順序/スコア）と例外が完全一致し、各加点・減点・遷移の合計が再計算できる。

### Phase 2 / P1 — 重複した安全処理だけを共通化

**PR-C：Span・保護区間・明示ロックの契約化**

1. `Utf16Span`の境界チェック、surrogate検証、URL/メール保護、明示EN/JA範囲の矛盾チェックを**仕様表とテストケースに先に固定**する。特にURL内のメール、同一ロック重複、交差・包含するロック、Unicode途中境界、`Protected`と`MeltypeEnglish`の優先順位。
2. `BoundarySpanValidator` / `ProtectedSpanDetector`のような**内部共通部品**へ抽出するが、既存方式ごとの違いは互換アダプターで維持。3方式すべてを一括で差し替えない。
3. 既存Windows Previewに挙動差が出た場合は「単なるリファクタリング」としてマージしない。別の要件・再現テストとレビューを必要とする。

**合格**：各方式の既存テスト・103件のスパン/スコア完全一致、URL/メール・ロック・UTF-16境界の追加契約成功。

### Phase 3 / P1 — 実測に基づく割り当て削減とビーム改善

**PR-D1：`CanRead`とローマ字パスを最適化**

- 公開`CanRead(string)`は残し、内部にSpan版の音節照合/有限状態遷移を導入。全ASCII大小文字、`nn`、促音、小書き、途中未完成、`ci/cye`等の結果が一致するか比較する。
- `Substring`、正規化文字列、配列生成を可能な箇所で削り、同じraw内の`(start,length)`ごとの読みやすさ・文字尤度をmemo化。キャッシュはraw/辞書/証拠変更で破棄し、別のユーザー入力へ漏らさない。
- 速度だけでなく**割り当てバイト数・実行時間・正解経路の完全一致**を示す。

**PR-D2：ビーム保持と候補重複の削減**

- 現行ソート方式を基準に、固定長候補集合またはヒープ/順序付きバッファを独立比較する。`Width=16`前提なので、ヒープ導入より小配列の線形最小値置換が速い可能性も測る。
- 同点スコアのタイブレーク、Top-Kの多様性、バックポインタ生存条件、確定済み経路と未確定経路の順序、Unicodeを再チェック。古い仕様への**完全出力互換**をまず目指す。
- 速度改善の主因を`CanRead`と決めつけず、CPU/割り当てのボトルネックをプロファイリングで確認する。

**合格**：各PRでPhase 0の出力完全一致、短文/長文/編集の測定表に退行と改善を明記。環境ノイズが大きい場合は効果を断定しない。

### Phase 4 / P1 — 汎用探索エンジンの設計と段階的移行

**PR-E：共通Decoderの仕様と互換実装**

- 分割候補の生成（JA音韻/EN語彙/Neutral）、特徴量計算、遷移制約、Top-K保持、タイブレーク、経路復元を**独立したインターフェース**で分ける。`CandidateProvider`・`Scorer`・`LatticeDecoder`などの名称は仮で、実装前の基本設計レビューで確定する。
- H10/H11の前向き状態付き探索と、v0.8の後ろ向き・区間数多様性優先探索は**同一アルゴリズムではない**。v0.8を無条件に新Viterbiへ移植しない。まずH11のみを新Decoderへ移し、旧H11を比較オラクルとして固定。次にH10と従来Coreを必要に応じてアダプター化。
- 候補の網羅性と正解経路の保持を分ける。単一`Top1`だけでなく`Top-K`・明示ロック・同点・不確実性・最大入力長・例外の互換性を契約化。
- **H12用にコピーを増やさない**。H12で選ぶ新しい特徴量は、共通基盤が成立した後の次期要件定義で検討する。

**合格**：移行対象モデルについてPhase 0の**全観測可能な出力が一致**。差分を伴う場合は「変更の意図・受け入れ条件・実験値」を別PRに分離。

### Phase 5 / P1 — 増分再解析の研究設計

**PR-F：仕様と正当性のオラクル → 実験実装**

- キャッシュの単位を**入力のUTF-16境界、英字run、ローマ字状態、候補辺、DP状態**で比較。変更位置に依存する右側/左側の読み直し範囲を計算し、接尾辞候補・境界切替やURL伸長などで影響が伝播する場合は安全に全再計算へフォールバックする。
- Insert/Backspace/Delete/中間編集/貼付け/絵文字/大文字切替/証拠ロック変更/元に戻すを含む編集列を生成。`H10PrototypeSession`等の**毎回全再解析**を正しさのオラクルとして保持する。
- 差分方式と全再解析で`Top1`だけでなく`Top-K`・スコア・明示ロック・入力raw・キャレットUTF-16座標が一致することを確認する。

**合格**：編集列と長文での正しさが一致し、実測で処理時間・割り当て量が改善。高速化のために辞書や候補を意図せず省略しない。

### Phase 6 / P1〜P2 — 精度の一般化検証と重み学習の判断

**PR-G：層別分析・独立holdout・学習の実験要件**

1. 辞書命中/非命中で候補被覆・Top1・Top-K・純日本語誤ENを分ける。辞書あり/なしのアブレーションは、**辞書が入力の一部でもある仕様上の差**と明示する。
2. Phase 0で確保した独立holdoutのラベル・意図衝突・会話文脈を管理し、devだけで試作。学習済みモデル・特徴量・ハイパーパラメータ・分割シード・辞書版を記録。testは最終判断にだけ使用する。
3. ルールの無秩序な加点を増やさず、辞書・音韻・文脈・切替コストを**名前付き特徴量と重みセット**に分離する。ロジスティック回帰（候補2値判定）だけでなく、経路全体の相互作用を扱う**構造化の重み最適化**も比較対象にする。
4. EN-OOV、日英助詞、固有名詞、ローマ字の表記揺れ、文脈不足、負例、長文、非ASCII、最悪遅延を別々に評価。見かけの総Top1だけで採用しない。

**合格**：独立集合で現行H11より**日本語保護を悪化させず**意味のある改善を確認、評価用データの独立性・モデル学習履歴がMarkdownで再現可能。

### Phase 7 / P2 — Windows Previewへ導入する前の製品化ゲート

- 次期要件定義で**H11系をどのホスト境界に、どの条件で接続するか**を決定するまでは、研究エンジンを既定の打鍵・確定処理へつながない。
- 実験ON/OFF、明示的なフォールバック、エラー時の安全な原文保持、Backspace、Enter確定、辞書・かな漢字、URL、メール、英日混在、長時間入力、パスワード欄などの安全試験を設計する。実機ログは機密を除去。
- 同じWindows端末・同じ設定・同じraw打鍵列で本家MeltypeとMeltiaの表示/確定/遅延を比較し、`Core`だけの境界精度とは**別レポート**に記録する。

## 5. 原則とマージ条件

1. **リファクタリングPRは挙動不変**：同じ入力、証拠、辞書バージョンで同じ`Raw/Edges/Routes/Score/NeedsConfirmation/AutoCommitAllowed`と例外。性能のみを変更する場合にもgold 103件全数が一致すること。
2. **精度改良PRは挙動差分を申告**：改善・悪化ケース一覧、純日本語誤英語、日英境界、候補保持、実測時間を添付。既知Issueに最適化した結果はholdout精度と混同しない。
3. **安全性の不変条件**：URL/メールを損なわない、UTF-16サロゲートを分割しない、明示EN/JAロックの矛盾を拒否する、rawを変更・自動確定しない、停止しない入力は時間/長さの上限を守る。
4. **レビューと並列開発**：各PRに対象ファイル・依存フェーズ・受け入れ条件を明記し、mainへマージした直後のSHAで比較する。別のPRで同じファイルを並列編集しない。外部AIレビューは参照可能だが独立検証する。
5. **再現可能な測定**：数値の表示時にサンプル構成・母数・機器・Release構成・CPU/.NET・コミット・反復数・辞書版・測定誤差を必ず記録。ベンチ結果の変化は同じ環境で再測定してから主張する。
6. **GitHub Actions／配布を触らない**：この計画書をもって本番の実験フラグ・Release・配布ワークフローを有効化してはならない。
