# Meltype上流変更の受け入れ・Meltia段階的リファクタリング方針（2026-10-17）

> **状態：提案・設計レビュー用（実装／移植／既定動作の変更なし）。** Meltiaの既存基盤を凍結して、今後のMeltype更新を機械的な一括マージではなく、要件・設計・テストを通した個別移植で受け入れるための規約。まず本書をレビューし、合意した範囲を次期バージョンの要件定義へ落とす。上流に追従すること自体を品質・機能の保証とはみなさない。

関連資料：[由来と分岐点](MELTIA_ORIGIN.md)／[既存アーキテクチャ整理](MELTIA_ARCHITECTURE.md)／[Windows Preview](MELTIA_WINDOWS_PREVIEW.md)／[H11共通Decoderの採用ゲート](MELTIA_H11_PHASE4_MIGRATION_EXIT_GATES_20261017.md)／[研究データ](https://github.com/Fugu0141/IncrementalBoundaryLab)。

## 1. 方針の核

1. **ベースを崩さない**：現行Meltiaの `main` と、Meltypeから継承した原コードの動作を比較オラクルとして保持する。上流コードを無条件にコピー・rebase・mergeして既存実装を置換しない。通常の確定・入力・学習・更新の挙動を設計PRで変更しない。
2. **機能として受け入れ、構造はMeltiaに合わせる**：上流の仕様と修正意図を確認し、Meltia側の責務分離・安全契約に沿って移植する。実装をそのまま取れる場合でも独立性・依存・ライセンス・テストを確認する。「同じ機能」と「同じ内部コード」は別である。
3. **境界判定研究は独立させる**：`src/Meltia.Core`のH系モデル、候補生成・探索・Top-K・研究ベースラインを保護する。`src/Meltia.CompositionBridge`等で上流のcompositionとの境界を定義し、上流の巨大クラスにMeltia固有判断を増やさない。共通Decoderの本番切替は専用の採用ゲートが満たされるまで行わない。
4. **取り込み、純粋なリファクタリング、動作変更を別PRに**：同時に混ぜると不具合の原因を追跡できない。上流の不具合修正とMeltia固有ロジック修正も別PRにする。
5. **独立製品としての識別子・権利・安全を優先**：Meltiaの設定保存先、実行名、起動時登録、終了制御、更新、将来のGUID/TIP/パイプを上流に戻さない。原著者表示・SPDX・第三者のライセンスを保持する。上流のインストーラーをMeltiaとして使わない。
6. **常に再現可能にする**：上流PR番号だけでなく、採用する特定のcommit/tag、差分、元コード、テスト、判断結果をMarkdownに残す。最新mainの可動ターゲットをそのまま開発ベースにしない。

## 4. 上流変更の分類・採否

PR/commitは既存の「修正」「機能追加」「辞書」のような**変更目的**で分類し、そのほかに**変更対象**（Core / 入力・表示 / ネイティブ / 設定・配布 / OS / テスト）と**リスク**（通常・高リスク・導入禁止状態）を独立して記録する。分類は「採用承認」ではない。

| 判定 | 典型例 | Meltiaの扱い |
| --- | --- | --- |
| A. 変更なし／既に同等実装 | 完全一致、またはMeltiaで既に問題解消済み | `covered`としてコード移植せず、根拠テストと比較結果のみ記録 |
| B. 互換な局所修正 | 最小の修正、純粋関数、独立テスト | 1目的/1PR。可能なら上流の変更を忠実に取り込み、既定挙動との互換性を検証 |
| C. 責務分離後に移植 | CompositionController、判定、設定・学習の複合変更 | 最初に挙動不変の抽出PR、その後に機能移植PR。Adapterで依存を閉じ込める |
| D. 新しい振る舞い／機能 | 辞書にない新機能、UI、IMEモード、学習変更 | **次期バージョン要件定義で採否を決定**。採用しても既定ONは独立判断 |
| E. データ（辞書・モデル） | 英語/日本語辞書、候補順位辞書、第三者データ | 出典・ライセンス・サイズ・再現性・誤変換を独立評価し、コードと別PR |
| F. 高リスクな連携・配布 | native TIP、フック、設定移行、更新/インストール、配布workflow | 既存設定・本家との共存を守るMeltia専用設計の審査が先。現Previewへ無条件コピー・自動実行は不可 |
| G. 不採用／保留 | 仕様不整合、証拠不足、既存安全契約と衝突 | `deferred`または`rejected`。理由と次回再検討条件を記録 |

**優先順位**はP0: 入力消失・誤削除・権限/秘密入力の危険、P1: 既知の再現可能な既存機能退行、P2: 保守性・互換性・独立性向上、P3: 機能追加・辞書拡張。ただし**上流の高リスクパッチを急ぎ本番へ入れるという意味ではない**。P0でも隔離・テスト・ロールバックを先に用意する。

## 5. 将来の更新を受け入れる手順（必須）

1. **基準を固定**：Meltia main SHA、上流の前回採用済みSHA（未設定なら分岐祖先）、上流候補のtag/commit、対象OSとバージョンを記録。上流のopen PRはMerge済みのように扱わない。
2. **変更を棚卸し**：上流差分をcommit/PR→ファイル→機能・副作用の関係へ分解。各変更にA〜G、責務・リスク、Meltia独自差分との衝突、候補の採否理由を記録。巨大PRは独立変更単位に分割する。
3. **要件定義（Markdown）**：何を移すか/移さないか、既存と意図的に変える振る舞い、失敗時のfallback、ユーザーデータ・既定動作・辞書・ライセンスへの影響、受け入れ条件を決定。ここで合意しなかった新機能は実装しない。
4. **基本設計（Markdown）**：ネイティブ／ホスト／Composition／検出器／Meltia Core／辞書・永続化のどこに変更を置くか、引数と戻り値・UTF-16/イベント順/同期・非同期/副作用の境界、テストオラクルを記述。上流コードの欠陥があれば**意図的な振る舞い変更を別PR**へ分離する。
5. **オラクル固定**：移植前のMeltiaと対象上流の必要な振る舞いを、同じraw/evidence/辞書SHA/環境で保存。仕様差を「元からある相違」「採用する変更」「事故」に分類。旧Meltiaテストだけで上流修正の正しさを証明しない。
6. **小さく実装・PR**：純粋な責務分割→互換Adapter→上流修正→必要な機能有効化の順。Meltia独自ファイル/ディレクトリ、他チャットの作業に関係ないファイルを触らない。機械的移動とバグ修正を混ぜない。
7. **検証とコードレビュー**：対象Core/Composition/OSのReleaseテストとstrict-quality、同値・否定/例外・性能比較・Windows実打鍵（入力に影響する場合）。旧仕様から変わる場合は新ゴールドと理由を別PRで承認。CIの無フックsmokeは実打鍵の代わりにならない。
8. **Mergeと追跡更新**：未解決の重大指摘がなく、対象ゲートに合格した場合のみMerge。取り込み済み上流PR/commitと採用範囲を台帳に追加。**上流の「追跡済み先頭」を不用意に進めない**：一部だけ選択移植した場合は上流の未採用変更を残し、次回比較で再発見可能にする。
9. **不具合・巻き戻し**：問題を検知したら独立フラグOFF・旧判定へfallback（用意してある領域のみ）、必要なら当該PRのrevert。ユーザー辞書/設定の移行が不可逆になる変更は別承認と明確なバックアップ・復旧手順を要する。

各PRの申し送りは [上流取り込みチェックシート](MELTIA_UPSTREAM_INTAKE_TEMPLATE.md) を複製して記録する。上流からそのまま取り込む場合は採用元の原commit/PRとGit履歴を残し、必要なら `git cherry-pick -x` を検討。Meltia向けに手動で移植する場合も元の作者・SPDXと上流の採用根拠を明記する。コミットを選ぶときはPR全体の前提変更・依存PRも確認する。

## 6. 検証基準と段階的リファクタリングの順序

**まず変更前の挙動を測る**。共通の固定試験に加え、対象に応じて以下を実施する。

| 対象 | 最低限の比較・安全試験 |
| --- | --- |
| 検出器・境界 | 原文・UTF-16区間の完全保存、候補全順/重複/score、全Top-K、明示EN/JA/保護、URL/メール、例外、103件凍結ベースライン、長文/emoji/日本語・英語混在、独立holdout |
| 逐次入力・状態機械 | KeyDown/Up、リプレイ、確定/未確定、Backspace/Delete、キャレット・フォーカス移動、再変換/修正、学習/Undo、UI再表示、順序と文字消失なし |
| 設定・辞書・学習 | 保存先の独立、フォーマット互換・旧データ不変更、辞書の著作権・出典、確定前後の学習、復旧・繰返し実行 |
| Windows/TSF・ネイティブ | Windows Previewのビルド・hook-freeスモークに加え、別途実機打鍵、競合・権限・例外・秘密入力、Meltia専用GUID/COM/登録の事前監査、Meltype共存 |
| 全体品質 | CI／既存テスト、同一runnerでの旧・新ペア性能計測（p50/p95/p99と割当・長文32〜1024）、配布物・更新・ライセンス監査 |

**予定する作業フェーズ（順次PR、採用前レビュー）**

- **R0：差分棚卸し（文書のみ）**。B→U(v1.2.1) / B→Mの三方比較。対象78ファイルを所有領域と採否で台帳化し、まず修正系と本家テスト変更を選別する。採用不可・重複を可視化。
- **R1：互換テスト・継ぎ目の設計**。特に `CompositionDetector`、`CompositionController`、`MeltypeSession`、`Meltia.Windows` の契約・副作用・所有を固定。大規模な名称変更やファイル移動は避ける。
- **R2：低リスク純粋処理の整理**。新旧同値テスト付きで、候補の計算・読み・表示データ等を副作用から離す。`partial`でファイルが分かれても共有状態が残ることに注意。
- **R3：v1.2.1までの選択移植**。P0/P1の修正→Coreの互換変更→必要なUI・辞書/学習変更を、条件付き・小さなPRで取り込む。上流のテストを同時に移すが、上流仕様がMeltiaと異なる場合は比較経路に隔離する。
- **R4：次の固定上流タグを選ぶ**。v1.2.2-pre.1や更新後mainを、**改めて固定SHA・依存関係・レビュー状態で評価**。v1.2.1との差分を一括マージせず、同じ台帳を更新して繰り返す。
- **R5：OS・製品固有の移行（独立計画）**。TSF/IME登録・配布・更新はMeltia独立性を優先する専用要件と実機E2Eを揃えてから進める。

## 7. マージ・作業の停止条件

- Meltiaの既定入力・確定・表示・学習が、意図しない形で変化した。
- 保存先/GUID/通信経路/更新がMeltypeを指す、または上流リリースへ誤公開する可能性がある。
- 独立Windows Previewと正式TSFの境界を越えて、登録・更新・インストーラー・hooksを未検証のまま実行する。
- UTF-16・文字欠落/重複・URL/メール保護・例外・フォールバックの契約に退行がある。
- 精度差・速度差が存在するのに「リファクタリングで挙動不変」として説明している。
- 上流作者の変更とMeltia独自ロジックを混ぜて原著作権、依存やレビュー範囲が追えない。
- 人手・実機テストが必要な変更について、CIだけで完成と主張している。

## 9. 本文書の承認条件

- 上流の固定commit、Meltia既定動作、責務境界、変更分類、停止条件についてレビュアーの合意が取れていること。
- 次期実装に先立ってR0の対象リストを個別チケット化し、要件定義→基本設計→実装→不具合修正の順序に戻れること。
- **今回のPRはMarkdownのみ**。コード、辞書、ネイティブ、Actions、実験モデル、ビルド設定は一切変更しない。文書がMergeされてもv1.2.1へのコード追従が完了したわけではない。
