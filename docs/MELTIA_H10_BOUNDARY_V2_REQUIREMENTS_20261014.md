# Meltia H10 / Boundary v2 要件定義（研究フェーズ、2026-10-14）

> **状態: Draft / 設計と測定条件の定義のみ。** 現行Meltiaの入力経路は変更しない。正式TSF、Windows Previewの既定設定、Meltype本家にも影響させない。新しい判定エンジンの改善率はまだ測定していない。

## 背景

Meltypeに蓄積された誤判定Issueには、辞書外英単語（[`infobesity`](https://github.com/yksr-melt/Meltype/issues/538)）、英語+助詞（[`githubya`](https://github.com/yksr-melt/Meltype/issues/440)）、日本語の過剰英語判定（[`mendokuseena`](https://github.com/yksr-melt/Meltype/issues/544)）、ローマ字解析（[`shatsu`](https://github.com/yksr-melt/Meltype/issues/594)）、構造的英字（[`.gitignore`](https://github.com/yksr-melt/Meltype/issues/431)）、文脈・学習（[`new` / 「ねw」](https://github.com/yksr-melt/Meltype/issues/491)）など別方向の誤りがある。既存方式に新しい語や助詞ルールだけを追加すると、英語検出増と日本語破壊がトレードオフになり得る。

現行Meltia独立Coreでは、`MeltiaUnknownLatinCandidates`の読み切り・候補長/ラン長による打ち切り、`MeltiaPhoneticLatticeDecoder`の音韻辺長・探索幅制約、固定助詞とフランク減点が残る。研究時の制約として合理的でも、任意の新しい英語と日本語に汎化できることは証明されていない。

**研究基盤・Issue由来47件・評価器**: [IncrementalBoundaryLab H10 Draft PR #10](https://github.com/Fugu0141/IncrementalBoundaryLab/pull/10)、[研究ノート](https://github.com/Fugu0141/IncrementalBoundaryLab/blob/research/h10-issue-driven-boundary-v2-20261014/research/2026-10-14-h10-issue-driven-boundary-v2.md)。

## スコープ

**今回（研究/要件定義）**: 生打鍵列からの日本語・英語・構造的Latin・記号の境界候補生成、経路探索、スコア付け、不確実性、増分更新のアーキテクチャを再設計し、現行Coreに対する独立評価を用意する。

**今回対象外**: 辞書の網羅性改善そのもの、Mozcの文節変換、全角句読点表示、キーボードフック・TSF登録・フォーカス制御、IMEインストーラー、ユーザーデータの自動収集。これらのIssueは引き続き別トラックで扱う。

## 機能要件

| ID | 要件 | 受け入れ判定 |
| --- | --- | --- |
| H10-R01 | 原文（大/小文字、未完成ローマ字、記号、英数字）とUTF-16位置を無損失で保持 | 任意の候補/上位経路が原文の全区間を重複・欠損なくカバー。サロゲートを分割しない |
| H10-R02 | 日本語音韻候補と英語綴り候補を独立に生成 | 短い英単語・全体が日本語としても読める単語にも双方の候補が存在し得る。辞書外語を強制確定しない |
| H10-R03 | URL、メール、拡張子、識別子、数値、既存の漢字と記号を保護 | 保護対象に対する境界/文字列破壊なし。ホストと同じ範囲を強制できる |
| H10-R04 | 英語＋助詞、日本語＋英語、英日英など複数の切替を同時評価 | 候補発見率、Top-K gold生存率、Top1一致率、境界F1を**別々に**報告 |
| H10-R05 | 日本語だけの長文・崩し言葉・未完成ローマ字を英語に過剰吸収しない | 純日本語の偽Latin区間率を単独測定し、既定Coreからの退行を停止条件に含める |
| H10-R06 | 文脈・利用者の明示Latin/日本語意図を一時証拠として扱い、同一rawを単一ラベルに固定しない | `new`などの対照意図ケースと手動ロックを診断。文脈なしに絶対正解とは主張しない |
| H10-R07 | 増分入力とBackspace/範囲編集の結果が、同じrawを改めて解析した結果と整合 | 入力系列・途中状態・確定後書換え禁止をテスト。必要に応じて候補表示だけ変更可 |
| H10-R08 | 局所な早期確定による不可逆誤変換を抑える | **候補のスコア差＝確率とみなさない**。確定前の保留/明示確定を分ける。新Coreは勝手にホスト文字列を書き換えない |
| H10-R09 | 既存v0.5〜v1.0-dev、現行Preview、本家Meltypeの安定動作と比較可能 | 旧版を残し、実験フラグのみ。新方式を既定ONにしない |
| H10-R10 | 実行時間と割当量を測定可能な増分更新 | 32/128/256文字・編集操作・多重切替でp50/p95/p99を既存と同一条件比較。複雑性を調査 |

## 基本設計の候補（未採用）

1. **Immutable Raw / Context**: 原文の位置とユーザー意図ロックを唯一の基準とし、正規化文字列は学習器の特徴量に限る。
2. **Dual-channel proposal graph**: 日本語ローマ字の有限状態音韻解析と、辞書内外の英語サブワード候補を別々に生成。構造的なLatin/URL/漢字/記号の辺を合成し、フォールバックも残す。
3. **Joint language-boundary decoder**: 単語ごとの「英語かどうか」から、言語区間/境界の全体経路スコアに転換する。日本語保持・英語保持・遷移確率を別々に学習・調整。
4. **Incremental uncertainty & commit policy**: Top-Kだけに依存しない境界不確実性を検証し、編集点周辺だけ再解析。確定済みアプリ領域を自動で改変しない。

以上は実装確定案ではない。H10a/bの実験で採否を判断し、過去のローマ字FSTやMeltype由来コードを無条件に廃棄しない。既存機能は技術的な権利・ライセンスを維持する。

## 評価・試験・レビュー

1. **H10a: 誤判定の診断基盤**: 本家Issue由来47件のraw意図を診断データとして固定。IssueとMeltiaでの再現は区別する。英語区間なしケースも集計する。入力フォーカス不良など境界外のIssueはスコープから除外する。
2. **H10b: 候補生成比較**: gold区間候補が生成されない例を特定し、英語候補下限・辞書ヒット・大文字・構造候補・音韻FSTをablationする。候補数・割当量も測る。
3. **H10c: 全経路判定比較**: 候補はあるのにTop-Kから漏れる例、Top-KにはあるのにTop1が負ける例を分類。旧版と同じ辞書条件/seed/閾値調整無しholdoutで比較する。
4. **H10d: 逐次入力と実機試験**: Backspace・途中の英字/日本語挿入・確定とイベント順序、長文・編集時の遅延/メモリ/二重入力を区別。CIで性能が良くてもWindows実キーの合格を省略しない。
5. **採用ゲート**: 新方式が純日本語・未知英語・英日混在のいずれかで悪化する場合、合算平均の改善で相殺しない。10,000件以上の生成ストレスは属性テストとして維持し、別に独立人手goldを追加する。学習データの辞書ライセンスとtrain/dev/test汚染もレビューする。

**最低限の結果形式**: Git SHA / .NET SDK・OS / 入力モード・辞書 / コーパス出典・seed・train/dev/test分離 / 候補recall / Top-K / Top1 / JA誤EN / 境界F1 / CER（別測定） / 編集時の誤確定 / p50-p95-p99 / GC割当 / 全失敗例。単独Issueが通っただけで改善宣言しない。

## 実装・マージ方針

- 研究成果は **IncrementalBoundaryLabへ記録**し、H10が評価を満たすまでMeltiaのProduction/Previewの入力経路に移植しない。
- 移植時は最新`main`から専用ブランチを作り、設計・実装・回帰テストを分離。旧Coreまたは旧判定ルートを参照実装として残し、双方を同じテストで比較する。
- 本家Meltype Issueで確認されていないMeltiaの再現結果を推定で書かない。Issueごとの場当たり的な辞書追記は別修正で行う。
- 本書のレビュー完了後に基本設計を更新し、研究PRと製品側実装PRを独立してレビューする。mainへの自動Mergeはしない。

## 現時点で証明できないこと

- 新アルゴリズムの実装はこのPRにない。精度や入力速度の改善結果は**未計測**。
- 本家Meltypeの各報告がMeltiaでも同じ表示になるとは限らない。
- 同一の打鍵系列から異なる入力意図を常に特定することは、追加文脈なしでは理論的に不可能。ユーザーによる選択・修正を残す。
