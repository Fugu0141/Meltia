# H10: 未知英語候補の生成と多区間解析（2026-10-12）

## 目的と対象

Meltia Core の未知英語検出率が低く、正解区間がラティスに存在しないことが根本的な問題だった。
既存の[47件・530件合成評価](MELTIA_BOUNDARY_EVALUATION.md)の正解span候補包含率を改善する。
本変更は **Meltia.Core のみ**。Meltype本体、入力UI、IME/TSF、Mozc、インストーラー、
ユーザーの確定文字列へ一切影響しない。

研究版の有効化:

```csharp
var engine = new MeltiaBoundaryEngine(new MeltiaBoundaryOptions(
    ExperimentalUnknownLatinCandidates: true));
var diagnosis = engine.Analyze("kinouhastrategywakaru");
// Candidate(7,15) のような英字仮説を取得できる。
// ただし Top1 は日本語のままの場合があり、AutoCommitAllowed == false。
```

**オプション未指定（既定）の挙動は以前と同じ。**
H10を有効化した場合は、過剰な英字断片への飛びつきを防ぐため、必ず
英字区間ごとの保守的な4.5点の分割コストを適用する
（`ExperimentalFragmentationPenalty` を別途指定しなくても同じ）。
既存の辞書／Meltype／大文字候補とspanが重複する場合、H10はもとの候補を
**上書きしない**。最大128件の候補枠でも既存候補を先に採用し、
余裕がある場合にのみH10仮説を追加する。

## H10候補生成

`src/Meltia.Core/Boundary/MeltiaUnknownLatinCandidates.cs` に独立実装:

1. UTF-16原文のASCII英字連続部分を取得。1区間96文字を超える場合、
   推測候補生成を飛ばす（長文では既存の動作を維持）。
2. 連続部分全体が日本語ローマ字として成立する場合、候補を作らない。
   `nihongo`・`dokoniakerusonomamakyouno`などの誤切断を防ぐため。
3. 5〜24文字の部分区間を走査し、日本語ローマ字の読みを持たない綴りを候補にする。
   必ず左側が日本語ローマ字として読めるか、日本語の助詞・語尾の直後であり、
   右側もローマ字として読めるか、助詞・語尾が始まる位置であることを確認。
   `kinouha|strategy|no|requirement|toiu` のように先行部分に英語が混ざっても、
   助詞などを足場として後ろの英語候補を生成できる。
4. 候補の前後が日本語として成立する、助詞境界がある、文字数が適切といった
   独立の信号で保守的に順位づけ。**正解ラベルや研究54単語の一覧をコードに埋め込まない。**
   英語仮説のスコアは低く、辞書・Meltype由来の十分に強い候補より優先しない。
5. 候補集合は従来どおり最大128、探索経路は最大8、入力長は最大1024 UTF-16単位。
   必須ロック／URL・メール保護／UTF-16サロゲートペア安全性／編集後の再解析は維持。

`H10` の限界：未知英語がローマ字として読める場合（`feature`・`database`等）は
候補生成を抑止する。逆に日本語の長文が偶然ローマ字として成立しない場合、
偽の候補が出る可能性がある。また英単語の実際の長さを知らないため、
本物の境界の左右にずれた**多数の候補**が生じる。

## 比較の証拠

- 研究元：IncrementalBoundaryLab のH1〜H9に登場した54英語語種／19日本語音韻語種。
- 47件は本来の課題例、530件は異なる接続テンプレートを使う合成追加評価。
  **同一語彙を研究に再利用しているため独立した自然文holdoutではない**。
- Gold は raw UTF-16半開区間。人手で見知らぬ実文章を確認したgoldではない。
- すべてオフラインC#の結果であり、Windows実IME、Mozc、逐次打鍵遅延、
  C#/Python H9モデルのパリティは検証していない。
- 候補包含率は「gold英語spanのうち、候補一覧に完全一致するspanの割合」。
  **Top1表示精度ではない**。さらに候補に含まれる間違いの数も別に監視する。

**候補の過剰生成（欠点も測定）:**
540正解英語spanを含む530ケースで、辞書もMeltype予測も使用しないH10は
正解spanのうち505件を検出した一方、候補は合計**12,263本**。
goldに完全一致した候補の比率は**4.1%**。候補が多いことは入力精度の向上とは
等価ではない。誤候補を減らす文字モデル／語境界学習が次の課題。
この値の分母は「全ての候補span」であり、IMEが実際に選んだ誤確定件数ではない。

### 回帰検証

- Coreの独立H10候補契約：`strategy`、`requirement`、
  `knowledge.`、複数英語島、既存候補の保全、明示ロック優先、決定性、
  日本語のみ入力、長いASCII区間を検証。
- 評価ランナーは`Meltia-H10-independent`・`Meltia-H10-lexicon`・
  `Meltia-H10-shadow`・`Meltia-H10-shadow-lexicon`を追加。
  既存のモデル条件は削除していない。
- 日本語だけの分類でTop1誤英語入力が既定シャドーより増えるとCI失敗。
  ただしその負例はS11の5件・R08の152件であって、未知の日本語一般を代表しない。
- 候補の格納元や採用順位を変えない保全修正後は別SHAで再測定する。

## 次の課題と採用判断

**現時点では本番採用不可。** H10は候補生成での大きな改善が見られるが、
候補過剰生成、短い語／曖昧な語、2・3英語区間のTop1選択の改善は残る。

次段階は、H1研究の**日本語vs英語の文字n-gramモデル**を、データ漏洩のない
訓練／評価分割でC#に実装し、H10候補の絞り込みと経路得点に使う。
目標は候補Recallと偽候補数を同時に評価し、実際のTop1精度向上へつなげること。
その後に新しい入力者・ジャンルで人手ラベル付きholdoutを作成する。

GUI・TSF・アプリの実装作業には入らない。


## H10保全パッチ後の再評価（2026-10-12）

[CI実行](https://github.com/Fugu0141/Meltia/actions/runs/38183672789)（`91c88510`）:
旧方式候補と衝突するH10仮説は旧候補の得点・出所を保持し、候補128件の上限でも旧方式を優先するよう変更した。

- 530ケース、辞書なしH10：**93.52%**のGold英字spanを候補に保持（前回と同値）、TopK **332/530**、Top1 **177/530**。
- 530ケース、同梱英語辞書共有H10：Gold候補 **99.44%**、TopK **330/530**、Top1 **251/530**。
- 530ケース、Meltype分割参考＋同梱辞書共有H10：Gold候補 **99.44%**、TopK **331/530**、Top1 **263/530**。
- 47ケース、辞書なしH10：Gold候補 **65.96%**、TopK **25/47**、Top1 **12/47**。
- 530ケースのH10辞書なし候補**12,263本**に対し、Goldと完全一致したものは505本（**4.12%**）。正解候補検出率の向上だけでは、表示される境界の改善とは言えない。
- 530件の日本語のみR08=152ケースでは、独立H10による英字候補の追加は0、Top1も152/152日本語のまま。辞書を利用する方式には元から日本語中の英単語候補があり、全方式で「候補そのものが0」ではない。
- 保護条件：候補Recallが元の同条件モデルより下がった場合、日本語のみの**候補数**が増えた場合、日本語のみの**Top1誤英語**が増えた場合、評価CIを失敗させる。さらに120件のseed固定Unicode・URL・複数英語・編集関連の不変条件をCoreで検証。

## 評価の故障段階（追加）

`Program.cs` が各モデル・各分類の`failureStages`を出力し、入力単位で次を区別する:

- `correct`：Top1とGoldが完全一致
- `candidate-missing`：Gold区間の1つ以上が候補一覧にない
- `route-or-topk-missing`：Gold区間は存在するがTop8経路にGoldの組合せが存在しない
- `top1-ranking-wrong`：Top8に正解経路はあるがTop1に採用されなかった
- `host-top1-wrong`：比較元MeltypeのTop1がGoldと異なる（同じ形式の候補一覧がない）
- `exception`：モデル実行に例外が発生

**`route-or-topk-missing` は単なる経路スコアの失敗を意味しない。**
枝刈り・隣接spanの競合・beam幅8の影響が含まれ、経路接続可能性の調査は別に必要。

次の研究版では、正解候補生成率を落とさずに偽候補数を削減し、TopKからTop1の選択性能を高める。
