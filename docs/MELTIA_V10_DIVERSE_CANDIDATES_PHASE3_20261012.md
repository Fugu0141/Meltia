# Meltia v1.0 フェーズ3 — 128候補予算の位置的多様性（2026-10-12）

> **研究用Draft・正式リリース不可。**
> v1.0品質強化フェーズ2 [PR #12](https://github.com/Fugu0141/Meltia/pull/12) に積み上げる
> フェーズ3。既定動作・IME・TSFへの接続は変えない。

## 改良対象

v0.7以来の`MeltiaBoundaryEngine`は最大128候補を保持する。
明示ロックは先に保護し、それ以外の候補を原則として
1. ホスト／辞書などの非推測候補
2. v0.7の未知英語候補
の順、グループ内は得点降順で上から残す。

長い日英混在のように仮説が多数存在すると、
スコアの高い**入力の一か所だけに候補128件が偏り**、
後半にある別の英語の正しい候補が採用されない可能性がある。
これは現在の並び替え処理から導かれる**設計上の危険**であり、
実際の自然文評価で測定した統計的誤差率ではない。

## 提案する優先順位（既定OFF）

新しい `ExperimentalDiverseCandidatePruning` を
`ExperimentalUnknownLatinCandidates` と共に指定した場合だけ
候補数上限に対する次の選別を行う。

1. **明示英語・URL・メールなどの必須span**を維持する。
   必須spanが128個以上のときは既存の上限・例外処理を守る。
2. **辞書・Meltypeのホスト提案などの非推測候補**を、
   従来と完全に同じ優先順で確保する。
3. 残った枠の**半分（端数切り上げ）**で
   得点が高い未知英語候補を確保し、極端なスコア退行を抑える。
4. 残りの枠では、元入力のUTF-16位置を
   **24単位ずつの開始位置帯**に分け、帯ごとに
   得点の高い候補からラウンドロビンで選ぶ。
   日本語ローマ字として完全に読める入力への未知英語候補を
   生成しない既存条件は維持する。
5. 全順序を確定して候補を返す。
   `AutoCommitAllowed`は常にfalse。

選別器は**128候補上限に達しない場合は従来の候補一覧と完全同一**。
`ExperimentalDiverseCandidatePruning=false`では前フェーズと同じ
候補生成・経路探索のまま。
候補のスコア付けも変えないため、これは**候補数の配分方式**であり
英語らしさを新しく推論する統計的モデルではない。

### 想定リスク

- 辞書やホストの誤候補が多ければ、それらが先に枠を占める。
- 遠い位置の候補を残す代わりに、以前選ばれていた
  **正解候補を失うこともある**。
- 「開始位置が多様」でも、候補の終了境界や意図の正しさを保証しない。
- 原文中の96文字超の連続英字を処理するフェーズ2と組み合わせた場合、
  候補数上限の影響が特に大きい。
- スコア0.75の不確実性レビューは未校正のまま。
  今回もTop1を安全に確定してよい根拠にはしない。

## テストと評価

### 直接契約テスト

`tests/Meltia.Core.Tests` に、
人工的に候補が特定の位置に集中した128件超の
**候補集合そのもの**を投入するユニット契約を追加。

- 従来のスコア順では消える遠隔区間の候補が、
  新選別では少なくとも一つ残ること。
- 非推測候補が従来と同様に保護されること。
- 入力候補の列挙順によらず結果が決定的なこと。
- 上限に達しない短文、純日本語ローマ字、手動ロック、
  元テキスト・候補128・Top-K8・非自動確定の契約。

これは選別アルゴリズムの**単体性質**の試験であり、
自然文での精度向上は示さない。

### 合成コーパス

従来の47＋530＋290＋56＋60＝**983件**に、
`CandidateBudgetCorpus.cs` の**新36件**を追加し、
合計**1019件**の人工的意図ラベル付き試験を用意した。

- B01・12件：入力の離れた複数箇所に英語区間
- B02・12件：英語候補を密集させる16区間の長い列
- B03・12件：完全日本語ローマ字の長い負例

旧`v1.0-windowed`と新`v1.0-diverse`について、
辞書なし・辞書あり・Meltype参照のみ・両方の4条件で比較する。

**測定項目**：
- Top1の完全一致、Top-K候補に正解が残っている率
- 正解spanの候補ヒット数、候補総数、Gold候補割合
- **新しく救えた正解spanと、逆に落とした正解spanを別集計**
- 新しくTop1が正解になったケース数と、不正解になったケース数
- 日本語のみの誤英語検出件数
- p50/p95/p99のオフライン解析時間、割当バイト数
- 保持した未知英語候補が分布する開始位置帯数と、
  `Truncated`の発生数

評価の目的は**差分を把握し、導入可否を判断すること**。
Top1や候補再現率が悪化する場合は
パラメータ調整／新方式棄却を選ぶ。
根拠が揃うまでデフォルト有効にはしない。

### ローカル実行

.NET SDK 10とPython 3.10+の環境でリポジトリのルートから：

```bash
python tools/run-meltia-quality.py --tier full
```

または候補選別だけに焦点を当てて：

```bash
dotnet run --project tests/Meltia.BoundaryEvaluation/Meltia.BoundaryEvaluation.csproj -c Release -- --output artifacts/budget-36.json --suite budget
dotnet run --project tools/Meltia.BoundaryBenchmark/Meltia.BoundaryBenchmark.csproj -c Release -- --output artifacts/performance.json
```

**現時点では.NET SDK 10の実行結果を取得できていない**。
従って1019件への合格・精度上昇・レイテンシ低下を
主張しない。既定の処理は従来と同じで、実用IME統合も保留する。
